# Meeting rooms booking service 

Сервис для брони переговорок

## Доменная область

Корпоративное бронирование переговорных комнат. Администраторы заводят переговорки и один раз задают для каждой расписание доступности (дни недели + интервал времени). По расписанию система сама нарезает 30-минутные слоты. Сотрудники смотрят свободные слоты по переговорке и дате, бронируют их на себя, отменяют свои брони; администратор видит все брони.

Ключевые правила:

- на один слот может быть только одна активная бронь;
- слоты одной переговорки не пересекаются по времени;
- нет расписания — нет слотов, переговорка недоступна;
- нельзя забронировать слот в прошлом; бронировать может только роль `user`;
- отмена брони идемпотентна;
- все даты и время хранятся и передаются в UTC.

## Стек

| Слой | Технологии |
|---|---|
| Язык | Go 1.25 |
| HTTP | REST (HTTP/1.1), роутер `go-chi/chi`, контракт в OpenAPI (`api/api.yaml`), серверный код генерируется `oapi-codegen` |
| Аутентификация | JWT (`golang-jwt/jwt`), хеширование паролей — `bcrypt` |
| БД | PostgreSQL 17, драйвер `pgx/v5`, транзакции — `avito-tech/go-transaction-manager` |
| Миграции | `golang-migrate` (SQL-файлы в `internal/infra/postgres/migrations`) |
| Фоновые задачи | `go-co-op/gocron` (досоздание слотов на горизонт) |
| Логирование | `log/slog` |
| Тесты | `testify`, `golang/mock`, e2e — `testcontainers-go` (Postgres в контейнере) |
| Запуск | Docker, Docker Compose, манифесты Kubernetes (`k8s/`) |

Архитектура — слоистая (clean architecture): `domain` → `usecase` → `infra` / `transport`.

## Основные сущности

- **User** — пользователь: `id` (UUID), `email`, `password_hash` (опционально, для входа по паролю), `role` (`admin` / `user`), `created_at`.
- **Room** — переговорка: `id`, `name`, `description` (опц.), `capacity` (опц., > 0).
- **Schedule** — расписание доступности переговорки (не более одного на комнату, после создания не меняется): `room_id`, `days_of_week` (1–7), `start_time`, `end_time`.
- **Slot** — 30-минутный интервал в рамках переговорки, сгенерированный по расписанию и сохранённый в БД со стабильным UUID: `room_id`, `start_at`, `end_at` (UTC). Пересечение слотов одной комнаты запрещено exclusion-констрейнтом.
- **Booking** — бронь слота пользователем: `slot_id`, `user_id`, `status` (`active` / `cancelled`), `conference_link` (опц., ссылка из мок-сервиса конференций), `created_at`, `cancelled_at`. Уникальность активной брони на слот обеспечивается частичным уникальным индексом.

Связи: `Room 1—0..1 Schedule`, `Room 1—N Slot`, `Slot 1—N Booking` (из них активна максимум одна), `User 1—N Booking`.

## Что реализовано

1. Аутентификация / авторизация
2. Роли: админ, юзер 
3. Создание, получение списка переговорок
4. Добавление расписания
5. Поддержка слотов 
6. Получение свободных слотов
7. Создание брони (с возможностью получить ссылку на конференцию)
8. Получение своих броней, отмена брони

## Генерация слотов

Для каждой переговорки, у которой есть приложение, приложение поддерживает инвариант: созданы и доступны слоты на горизонт в 14 дней от текущего момента (другой период можно задать конфигурацией).

Поддерживается это следующим образом:
1. При создании расписания создаются слоты на промежуток [now; now+14ней] (горизонт)
2. Фоновая работа, для каждой комнаты идемпотентно дополняющая горизонт слотами
3. Фоновая работа, идемпотентно заполняющая весь горизонт (запускается реже и при запусках приложения)
4. При запросе на получение доступных слотов комнаты на дату, которая находится вне горизонта, эта дата идемпотентно наполняется слотами
5. Все промежутки и тайминги можно задать конфигурацией

Выбрал данный подход для возможности быстрого чтения, так как большинство запросов будут попадать в дни с уже сформированными слотами. Тяжелая работа Repair будет запускаться во время с маленьким активом  

## Тесты 

Юз-кейс покрыты юнит-тестами на 85%+. Весь доменный функционал так же покрыт на 90%+

Также реализованы e2e тесты с флоу создания комнаты -> расписание -> листинг слотов -> создание брони, флоу отмены брони.

## Запуск

```bash
cp .env.example .env   # или просто make up — он создаст .env сам
make up                # postgres + миграции + приложение на localhost:8080
make seed              # тестовые данные (one-off контейнер из того же образа)
make down
```

Kubernetes: `k8s/` — ConfigMap (несекретный конфиг), Secret (пароли, JWT-секрет), Job для миграций, Deployment на 3 реплики с probe'ами, Service.

## Соответствие 12 факторам

### I. Codebase — одна кодовая база, много деплоев
Один git-репозиторий = одно приложение (бэкенд). Из него собирается один образ, который деплоится в разные окружения (локально через Docker Compose, в Kubernetes, в CI). Фронтенд — отдельное приложение в отдельном репозитории, общающееся с бэкендом по HTTP.

### II. Dependencies — явно объявлены и изолированы
- Все Go-зависимости объявлены в `go.mod` и зафиксированы в `go.sum`; сборка идёт в изолированном контейнере `golang:1.25.0-alpine`.
- Итоговый бинарник статический (`CGO_ENABLED=0`), не зависит от системных библиотек.
- База часовых поясов вшита в бинарник (`import _ "time/tzdata"`), поэтому приложение не полагается на `tzdata` в ОС-образе.
- Версии всех образов зафиксированы (`postgres:17-alpine`, `migrate/migrate:v4.18.3`, `alpine:3.23`); CLI миграций берётся в релизный образ из зафиксированной версии.

### III. Config — конфигурация в переменных окружения
- Весь конфиг читается только из env (`internal/config`): доступ к БД, HTTP-адрес и таймауты, JWT-секрет и TTL, параметры генерации слотов, cost bcrypt, уровень логов, таймаут остановки, доля отказов мок-сервиса конференций.
- Секретов в коде нет. Для локального запуска значения лежат в `.env` (в `.gitignore`), в репозитории — только шаблон `.env.example`. В Kubernetes несекретное — в ConfigMap, секреты — в Secret.
- Fail fast: отсутствие обязательных переменных (`POSTGRES_*`, `JWT_SECRET`) или некорректное значение (например, `JWT_TTL=abc`) — ошибка на старте со списком всех проблем, а не тихий откат к значению по умолчанию.
- Проверка «можно ли выложить код в open source прямо сейчас» проходит: в репозитории нет ни одного реального секрета.

### IV. Backing services — сторонние службы как подключаемые ресурсы
- PostgreSQL подключается только по адресу и учётным данным из env; чтобы переключиться на другую БД (managed, другой хост), достаточно поменять конфиг, код не меняется.
- Сервис конференций спрятан за интерфейсом `conferenceLinkProvider`; сейчас подключён мок (по заданию), реальный клиент подключается заменой реализации, а его адрес задавался бы тоже через env.

### V. Build, release, run — строгое разделение стадий
- **Build**: multi-stage `Dockerfile` собирает бинарники `app` и `seed` из кода.
- **Release**: образ (с тегом, например `mos1ck/meeting:v1.0`) + конфиг окружения (`.env` / ConfigMap + Secret). Образ неизменяем, один и тот же образ идёт во все окружения.
- **Run**: запуск готового релиза (`docker compose up`, Deployment в k8s). На стадии запуска код не меняется и не собирается.

### VI. Processes — приложение как stateless-процессы
- Процесс не хранит состояние между запросами: аутентификация через JWT (сессий нет), все данные — в PostgreSQL.
- Нет локальных файлов, sticky-сессий, in-memory кэшей, от которых зависит корректность. Любой запрос может обработать любая реплика.

### VII. Port binding — экспорт сервиса через порт
Приложение самодостаточно: HTTP-сервер встроен (`net/http` + `chi`), слушает порт из `HTTP_ADDR` (по умолчанию `:8080`). Внешний веб-сервер/контейнер приложений не нужен.

### VIII. Concurrency — масштабирование процессами
- Приложение масштабируется горизонтально запуском нескольких реплик (в k8s — `replicas: 3`), благодаря stateless-процессам (VI).
- Фоновые задачи (дозаполнение горизонта слотов) работают в каждой реплике, но защищены advisory lock в PostgreSQL (`internal/infra/postgres/advisory_lock.go`): одновременно задачу выполняет только одна реплика, остальные пропускают запуск. Так добавление реплик не приводит к дублирующейся работе, а при падении реплики блокировка снимается автоматически вместе с её соединением. Сами задачи вдобавок идемпотентны.

### IX. Disposability — быстрый старт и корректная остановка
- Старт быстрый: HTTP-сервер поднимается сразу, первичное заполнение слотов идёт параллельно и не блокирует обработку запросов.
- По `SIGTERM`/`SIGINT` — graceful shutdown: сервер перестаёт принимать новые соединения и дожидается текущих запросов, планировщик дожидается выполняемых задач, пул соединений с БД закрывается. Время ограничено `SHUTDOWN_TIMEOUT`.
- Устойчивость к внезапной смерти: все изменения идут в транзакциях БД, фоновые задачи идемпотентны — если процесс убит посреди задачи, её просто повторит следующий запуск.

### X. Dev/prod parity — окружения максимально похожи
- Везде один и тот же образ приложения и одна и та же СУБД: `postgres:17-alpine` в Docker Compose, в e2e-тестах (Testcontainers) и в CI.
- Нет «лёгких» заменителей для разработки (типа SQLite вместо PostgreSQL).
- Разница между окружениями — только в конфиге (III).

### XI. Logs — логи как поток событий
- Приложение пишет структурированные JSON-логи в `stdout` (`log/slog`) и ничего не знает о файлах и ротации — это задача окружения (`docker compose logs`, `kubectl logs`, сборщик логов).
- HTTP access-логи пишутся тем же логгером в тот же поток (с request id), а не отдельным текстовым логгером. Уровень логирования — через `LOG_LEVEL`.

### XII. Admin processes — административные задачи как разовые процессы
Административные задачи запускаются как разовые процессы из того же релиза (образа) и с тем же конфигом, что и приложение:
- миграции БД — `migrate.sh` в образе (`make migrate`, в Compose — сервис `scheduler-postgres-migrate`, в k8s — Job `k8s/migrate-job.yaml`);
- наполнение тестовыми данными — бинарник `seed` в образе (`make seed` → `docker compose run --rm meeting-scheduler ./seed`).
